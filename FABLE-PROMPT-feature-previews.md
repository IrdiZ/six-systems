## The feature to plan

The explainer shows N feature cards. When the mouse moves over a card, a small floating window
appears next to the cursor and follows it. The window plays a short looping clip of that feature in
action in the clinical tool. When the mouse leaves the card, the window fades out.

Plan these parts:

1. **Clip production.** Make one clip per feature, 3 to 6 s each, in a seamless loop, with no captions or
   short captions only. Reuse `video/render.py` and the timeline format: one scene per feature slug,
   with a smaller viewport or a zoom on the relevant panel. The clips must be regenerated by one
   command, so they stay correct when the UI changes. Compare the formats: MP4/WebM (H.264/VP9, muted,
   `playsinline`) vs GIF vs animated WebP. Compare file size, quality, Safari support and loop
   behaviour. Recommend one. Expect GIF to lose on weight; say so if it does. Set a size budget per
   clip and for the total.
2. **Hover window behaviour.**
   - Follow the cursor with `requestAnimationFrame` and a light easing, with no jitter.
   - Keep a fixed offset from the cursor. Flip to the other side near the viewport edges.
   - Do not cover the card text the user reads.
   - Fade in after a short hover-intent delay. Stop and unload the clip when it is hidden.
   - Show one window at a time.
   - Lazy-load the clips: load the poster frame first, then start the clip on hover intent.
3. **Other inputs.**
   - Keyboard focus on a card shows the window, anchored to the card (no cursor follow).
   - Touch devices have no hover: tap shows the clip inline in the card, or in a sheet.
   - `prefers-reduced-motion`: show a still poster with a play control, and no follow movement.
   - Every clip gets a text alternative.
4. **Constraints.**
   - Static GitHub Pages. No build step and no framework: vanilla JS and CSS, as in the rest of `docs/`.
   - Keep the explainer fast. Measure page weight before and after, and set a budget.
   - The repo is public: synthetic data only, fictional organisations, no real names, no screenshots of
     real hospital software.
   - Design: match the existing design language (shared top bar, `docs/style.css`).
   - Avoid patterns that look AI-generated: no glassmorphism or gradient glow, no bouncy spring
     animation, no decorative numbering, no eyebrow labels, no emoji.
   - Writing: Simplified Technical English (max 25 words per sentence, active voice). No em dashes.
     British spelling.

## Explore adjacent ideas, then rank them

List each idea with value, cost and risk. Recommend which ideas go into this plan, which ideas go
later, and which ideas to drop. Starting set (add your own):

- **"Try it live" next to each clip.** It opens the clinical tool at that exact view, with a seeded
  scenario (`?s=` plus a hash route). The visitor can then click through the real tool, not only watch it.
- **The same preview on other pages.** Use it on the system tiles of "The gap" (hover a source and see
  how its files arrive) and on the links in the clinical tool's management view.
- **Link a feature to the data.** Hovering a feature card highlights the facts it touches in a small
  status chart. Example: "Code and unit conversion" lights up the 460 Converted facts.
- **Before/after view for conversion.** A slider between the raw EDIFACT/HL7 text and the structured
  row. It shows the conversion as a still image.
- **One guided tour.** It plays all the feature clips in order, with one sentence each. It is a
  web-native version of the pitch video for people who will not watch a video.
- **Poster frames as share images.** Generate a still per feature and use it as the Open Graph image.
  Use the same stills in a one-page PDF for funders.
- **Clip freshness check.** A test in the build fails when a clip is older than the UI files it shows
  (reuse the render cache hashes).
- **Shared preview component.** One small `preview.js` that all pages load. It is not copied into
  each page.

## What the plan must contain

Write the plan to `six-systems/EXECUTION-PLAN-<date>-feature-previews.md`. The repo is public: do not name
real people or hospitals in it. It must contain:

1. The decisions, with one-line reasons: clip format, size budgets, the interaction spec, and the
   adjacent ideas you accepted.
2. Phases, each small enough for one PR, in the order of the dependencies. Clips come first, then the
   component, then the page integration, then the adjacent ideas.
3. For each phase:
   - the files it touches
   - the model tier for each task (haiku, sonnet or opus)
   - the acceptance checks
4. Verification as invariants, not "it looks right":
   - Every `data-feature` slug has exactly one clip and one poster.
   - Total clip weight is within the budget.
   - There are no console errors.
   - The window never leaves the viewport at widths 390, 768, 1440 and 1920. Check this with
     Playwright, which moves the mouse over every card near each edge.
   - Reduced motion and keyboard focus each have their own check.
5. The PR checklist from the parent folder's `CLAUDE.md`, per branch:
   1. Code plus lint.
   2. A code-review agent on the diff.
   3. A browser check on a real deploy of the branch.
   4. Push.
   5. A PR description with the review outcome.
6. Escalation triggers: the cases where the executor stops and asks for a Fable ruling. Examples: the
   clip budget is not reachable, or Safari loop or autoplay fails.
7. Open questions for Irdi. Keep these to the decisions only he can make.
